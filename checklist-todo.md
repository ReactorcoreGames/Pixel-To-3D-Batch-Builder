The build plan, split into sessions. `DESIGN.md` says **what** to build; this file says **in what order**. The real app is now the reference for how everything looks, what it's called and what the tooltips say. The clickable mockup in `mockup/` was the starting point (sessions 1–7) and is kept only as history: it's far behind the app, so don't follow it or change the app to match it.

## How the sessions are organised

- **The app runs at the end of every session.** Session 1 ports the mockup with its fake engine, and each later session swaps one fake part for the real one. There's never a long stretch where nothing works.
- **Risky parts come early.** The things DESIGN.md marks as "verify in prototype" (split-plane blending, slice prisms, pixel-clean rendering, normal maps) each get a session where they can be tried before anything depends on them.
- **The core library gets tests** (Vitest). The most important one is the round trip: write a sheet in Phase 1, read it back in Phase 2, and get the same object.
- **Sessions are sized to fit, not fixed.** If one runs short, pull the next session's first items forward; if it runs long, leave the rest ticked-off-or-not and note it at the bottom.
- **Browser first, Tauri later.** Sessions 1–6 run in the browser (`npm run dev`): files come in by drag-and-drop or file picker, and results go out as a zip download. Session 7 wraps it in Tauri for real folders, file watching and the exe.

## Session 7c: shape rework (Egg, Gem, ⊙ shaped ends)

Found during session 8's performance pass with `test sprites/stress 128/` (128×128 noise-filled rectangle, triangle, diamond, circle, donut). Done in session 7c (2026-10-03). Agreed with the user (2026-10-02): fix it properly in its own session.

**The problems (before this session's prototype):**
1. **Egg and Gem never reached their thickness on uneven outlines.** They were the ↔ cut and the ↕ cut combined, each deepest at the middle of its own column or row, so the model only reached full depth where a long column's middle met a long row's middle. A triangle as a Gem at thickness 128 came out about 68 deep; then Phase 1's settle loop (Phase 2 refits the cuts to the panels' boxes, which only show each piece's widest point) shaved more off and broke parts loose. A donut as Egg/Gem grew 8 chunks at its diagonals.
2. **⊙ shapes left loose rods.** A ⊙ cut fits the circle/diamond to the drawing's bounding box, and the "a cut never empties a line" rule kept one pixel in every emptied row/column, which on a triangle sat alone at the base corners and became rods through the whole thickness (the black wedges in the contact sheet).
3. **⊙ shaped ends have the same two-cuts problem as 1.** `endCuts` for a ⊙ tube are the ↔ and ↕ cuts combined, kept to the ends. `test sprites/stress 128/stress 128 caps.png` (Tube ⊙ / Diamond ⊙, both ends, 128 deep, 16 sides): the donut's caps break into spikes even in the voxels, and the Diamond caps on the rectangle and triangle get odd slanted faces. Rectangle, circle and diamond outlines are fine.
4. **The low-poly mesh of Egg and Gem can't follow non-convex row slices.** It lofts one ring (ellipse or diamond fitted to the row's spans) per row piece along ↕. A donut's rows above and below the hole are curved bands, so it fills them in: four "petals". More Round sides only makes them smoother, so it isn't the Sides setting (checked at 8 and 16).

**Prototyped before the session** (on top of `0401452`):
- `inflate` in `src/core/shape.ts` (Egg = round profile, Gem = straight profile): each pixel of the model seen along the thickness axis keeps a span centred in the thickness, `len = full × f(s)`, `s` = the pixel's distance to the outline ÷ the largest such distance (exact EDT, `emptyDistance2`), parity kept like `profiled`, never under 1 or 2 voxels. `applyShape` sends `ell` / `dpy` there, so Phase 1 (`buildPhase1Model`) and Phase 2 (`carveModel`) both use it and Phase 2 rebuilds Phase 1's model exactly. Result: every stress Egg/Gem is 128 deep and one piece; a circle Egg is an exact ellipsoid; the donut is a ring. The PSRC example balls, boulder and football look practically unchanged (the user checked the balls in the web app with their session and likes them).
- ⊙ cuts: `cutSlices` has a `keepLines` flag; `applyShape` turns it off for the `T` cut (lines are only kept when a piece would vanish entirely). `carveModel` no longer re-cuts ⊙ shapes (the hull already is the extrusion of the cut outline the sprite's own panel shows, and a repainted outline is kept). The triangle now gives the teardrop (Tube ⊙) and kite (Diamond ⊙) the user expected, with no rods.
- Mesh prototype `inflatedSolid` in `src/core/mesh.ts`: `Manifold.levelSet` over the voxel model's own half-span per pixel (bilinear between pixel centres, −1 outside), edge length `π × longest size ÷ Round sides ÷ PER_SIDE`, then `simplify(edge × SIMPLIFY)`, intersected with the axis solids. It follows the donut ring with no petals (about 200–1,000 triangles on the 128px stress shapes). **Temporary switches to remove:** `P3D_LEVELSET` (on = the level-set path; off = the old ring loft, currently the default), `P3D_SIMPLIFY` (default 0.3), `P3D_PER_SIDE` (default 2), read through `ENV` at the top of `inflatedSolid`.
- `test sprites/stress 128/stress 128 lowpoly.png` / `voxels.png` were regenerated with the prototype (voxels: inflate; low-poly: old ring loft). `stress 128 caps.png` is new, also only in the working tree. `CLAUDE.md` gained notes on the user's PSRC session file and the stress folder.

- [x] **Oblique camera type** (`CAMERAS` in `presets.ts` becomes `ortho` / `persp` / `oblique`). The look Advance Wars' battle sprites use: the drawn side faces the viewer flat-on, with level lines staying level, and the depth recedes sheared up and to the side, so the top and the front show too. No rotation can do this; it's a shear projection: screen x = x + k·z·cos α, screen y = y + k·z·sin α. Fits `render.ts`'s camera setup (`cameraAxes`); depth sorting and the camera-fixed light need a view direction for it, so derive one from the shear. To decide: the angle (a 2:1 pixel step, about 26.6°, keeps the receding edges pixel-clean, like the isometric preset; 30° or 45° are classic), the depth scale (cabinet ½ vs cavalier 1), which way it recedes (up-right or up-left, and whether Mirror flips it), and which face is the flat-on one (the drawn side, or the object's side for front-drawn sprites, as `ref` does for turns). Settings in the set editor appear only for Oblique, like the field of view for Perspective. Also the turntable? (Probably not: it spins.)
